# 医院叙事生成助手 — 数据接口规范文档（交付版 v2.0）

> **版本**：v2.0  
> **目标读者**：医院信息科 / HIS 厂商 / EMR 厂商 / 数据平台团队  
> **文档用途**：明确医院叙事生成助手与院方数据平台之间的 RESTful 数据接口边界、字段规范、数据质量与对接要求，供数据方开发或暴露接口时使用。  
> **修订说明**：本版在 v1.0 原始数据接口基础上，根据“数据存储、检索、基础计算由数据方负责，我方仅负责图表生成、大模型叙事结论撰写、前端呈现”的边界重新梳理，新增了统计聚合接口、患者全景接口与实时状态接口。

---

## 一、系统边界说明

### 1.1 职责划分

| 职责域 | 数据方（院方/数据平台） | 应用方（医院叙事生成助手） |
|---|---|---|
| **数据存储** | 负责临床数据、字典数据、实时状态数据的持久化存储 | 不持久化存储原始临床数据，仅临时缓存或用于前端展示 |
| **数据检索** | 提供按患者、就诊、时间、科室等维度的查询能力 | 调用接口获取数据，不做本地 SQL/图检索 |
| **基础计算** | 负责统计、聚合、排序、去重、基础指标计算 | 基于返回结果生成图表配置（ECharts Option） |
| **数据治理** | 负责数据清洗、归一化、脱敏、主数据一致性 | 按约定消费已清洗数据 |
| **知识图谱（可选）** | 可由数据方维护医疗知识图谱，也可由应用方基于数据方接口构建；如由数据方维护，则额外提供图谱查询接口 | 消费图谱子图/路径/统计结果 |
| **图表生成** | 不参与 | 将接口返回数据转换为 ECharts / 其他图表配置 |
| **叙事生成** | 不参与 | 调用大模型，基于接口数据生成分析结论、患者故事线、简报文本 |
| **前端呈现** | 不参与 | React / Streamlit 前端展示 |

### 1.2 接口分层

本系统需要数据方提供以下 **5 大类接口**：

| 分类 | 说明 | 典型接口数量 |
|---|---|---|
| **A. 基础临床数据接口** | 患者、入院、出院、检查、检验、手术、医嘱等原始明细数据 | 7~10 个 |
| **B. 统计聚合接口** | 面向 dashboard、报告、简报的预计算指标 | 12~15 个 |
| **C. 患者全景/叙事接口** | 单个患者的完整时间线、摘要、相似患者、风险评分 | 5~8 个 |
| **D. 实时状态接口** | 在院患者、床位、主管医生等实时数据 | 2~4 个 |
| **E. 字典与元数据接口** | 科室、药品、检查、检验、疾病、手术等维表 | 1~2 个 |

> **灵活性说明**：下方接口路径、字段名、分页参数为推荐约定。数据方可根据自身数据平台能力调整，但需在对接前与应用方确认字段映射与返回结构。若数据方能直接提供宽表、视图或更聚合的接口，可协商合并，但需保证字段完整、语义一致。

## 二、接口总体规范

### 2.1 通信协议

| 项 | 规范 |
|---|---|
| **协议** | HTTPS（生产环境必须）；HTTP 仅用于测试环境 |
| **架构风格** | RESTful |
| **数据格式** | JSON |
| **字符编码** | UTF-8 |
| **Content-Type** | `application/json` |

### 2.2 认证方式（任选其一，对接前确认）

| 方案 | 说明 | 请求头示例 |
|---|---|---|
| **方案 A：API Key** | 请求头携带固定密钥 | `X-API-Key: your-api-key` |
| **方案 B：Bearer Token** | 通过 OAuth2 / JWT 获取短期 Token | `Authorization: Bearer <token>` |
| **方案 C：双向 TLS / IP 白名单** | 仅允许应用方服务器 IP 访问，配合 TLS 客户端证书 | 需数据方网络侧配置 |

### 2.3 通用请求约定

- **时间格式**：
  - 日期：`YYYY-MM-DD`，例如 `2024-03-15`
  - 日期时间：`YYYY-MM-DD HH:MM:SS`，例如 `2024-03-15 09:30:00`
  - 避免使用 `2024/03/15`、`15/03/2024`、`Mar-15-2024` 等非标准格式
- **空值处理**：缺失字段请使用 `null`，避免使用 `"nan"`、`"None"`、`"NULL"`、`"未提及"` 等字面量；字符串字段可为 `""`。
- **数值类型**：数值字段直接返回数字类型，不要加引号变成字符串。
- **布尔类型**：使用 JSON 布尔值 `true` / `false`，避免 `"是"` / `"否"` 字符串。
- **分页**：
  - 请求参数：`page`（从 1 开始）、`page_size`（默认 1000，最大不超过 10000）
  - 响应字段：`total`、`page`、`page_size`、`data`
- **排序**：默认按时间字段降序（最新在前）；如需指定，可通过 `sort_field` 与 `sort_order` 参数，对接前确认。

### 2.4 通用响应格式

```json
{
  "code": 200,
  "message": "success",
  "total": 10000,
  "page": 1,
  "page_size": 1000,
  "data": []
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | 业务状态码，见 2.5 |
| `message` | string | 状态说明 |
| `total` | int | 总记录数（分页接口必填） |
| `page` | int | 当前页码 |
| `page_size` | int | 每页大小 |
| `data` | any | 实际业务数据，对象或数组 |

### 2.5 通用错误码

| HTTP 状态码 | 业务 code | 含义 | 说明 |
|---|---|---|---|
| 200 | 200 | 成功 | 正常返回 |
| 400 | 400 | 请求参数错误 | 缺少必填参数或参数格式非法 |
| 401 | 401 | 未授权 | API Key / Token 无效或已过期 |
| 403 | 403 | 禁止访问 | IP 不在白名单或权限不足 |
| 404 | 404 | 接口/资源不存在 | |
| 429 | 429 | 请求过于频繁 | 触发限流 |
| 500 | 500 | 服务器内部错误 | 数据方服务端异常 |
| 503 | 503 | 服务暂时不可用 | 数据方服务维护或超时 |

## 四、基础临床数据接口详情

> 以下接口用于患者全息视图、患者故事线、知识图谱构建（如仍由应用方构建）、科研筛选等场景。  
> 所有时间范围参数如无特殊说明，均指该业务记录本身的 **发生时间**（入院日期、检查日期、手术开始时间等）。

### A1. 患者列表/搜索

- **接口地址**：`GET /api/v1/patients`
- **请求参数**：

| 参数名 | 类型 | 必填 | 说明 |

| `age_min` | int | 否 | 最小年龄（岁） |

| `department` | string | 否 | 当前/最近就诊科室 |

## 九、数据关联与质量要求

### 9.1 数据关联模型

```
患者(patient_id)
  │
  ├─ 入院记录 ── visit_id ──┐
  ├─ 出院记录 ── visit_id ──┤
  ├─ 检查记录 ── visit_id ──┼── 共同构成一次就诊（Visit）
  ├─ 检验记录 ── visit_id ──┤
  ├─ 手术记录 ── visit_id ──┤
  └─ 医嘱记录 ── visit_id ──┘
```

### 9.2 关联字段一致性要求

| 字段 | 要求 |
|---|---|
| `patient_id` | 同一患者在所有表中必须完全相同（区分大小写） |
| `visit_id` | 同一就诊流水号必须对应同一患者，不同患者不能复用 |
| `medical_record_no` | 同一患者病案号建议保持一致，用于辅助校验 |
| `admission_date` | 入院表与出院表的同一 `visit_id` 入院日期应一致 |
| `department` | 科室名称应与字典接口中的 `name` 保持一致 |

### 9.3 必填项完整性

- `patient_id`、`visit_id` 在所有表中不能为空。
- 时间类必填字段（`admission_date`、`discharge_date`、`exam_date`、`submit_time`、`surgery_start_time`）空值率应低于 5%。
- 诊断、药品、检查、检验、手术名称字段应使用院内标准化名称，避免自由文本差异过大。

### 9.4 值域规范

| 字段 | 建议值域 |
|---|---|
| `gender` | `男` / `女` / `未知` |
| `is_drug` | `是` / `否` / `未知` |
| `result_hint` | `高` / `低` / `↑` / `↓` / `正常` / `偏高` / `偏低` |
| `discharge_outcome` | 治愈 / 好转 / 未愈 / 死亡 / 转院 / 其他 |
| `risk_level` | `高` / `中` / `低` |
| `abnormal_flag` | `true` / `false` |

### 9.5 特殊字段清洗建议

- 诊断名称中不要包含 `"检查"`、`"待查"`、`"随访"`、`"体检"` 等非疾病词汇。
- 药品名称中避免包含 `"（中选）"`、`"【中选】"`、`"（国采）"` 等采购标记。
- 主诉文本末尾避免 `"，下一周期化疗"`、`"，入院治疗"`、`"，复查"` 等治疗后缀。
- 数值字段不要混入单位、范围说明等文本。

## 十、同步策略

### 10.1 全量同步

- **场景**：首次对接、系统初始化、重建知识图谱、年度/季度报告。
- **方式**：按时间范围分批次调用基础临床数据接口，建议每批 5000~10000 条。
- **顺序**：入院 → 出院 → 检查 → 检验 → 手术 → 医嘱。
- **时间范围**：建议从有完整数据记录的最早日期开始，到当前日期。

### 10.2 增量同步

- **场景**：每日/每周定时更新数据概览、简报、风险预警。
- **方式**：通过 `start_date` / `end_date` 参数按日期增量拉取基础临床数据。
- **推荐频率**：
  - 每日凌晨 02:00 同步前一日数据
  - 每周一凌晨同步上周数据用于周简报
  - 实时状态接口按需查询或短周期轮询（5~15 分钟）

### 10.3 实时查询

- **场景**：患者搜索、患者全息视图、查房问答。
- **方式**：用户操作时直接调用接口，响应时间建议 ≤ 2 秒（患者全景摘要可放宽至 5 秒）。
- **缓存**：应用方可按业务需要缓存字典、统计数据，但原始临床数据以数据方为准。

### 10.4 数据更新通知（推荐）

如数据方支持，建议提供数据变更推送机制：

```
POST /callback/data-update
Body: {
  "event_type": "admission" | "discharge" | "exam" | "lab" | "surgery" | "order",
  "patient_id": "P000001",
  "visit_id": "V202403150001",
  "event_time": "2024-03-15 09:30:00"
}
```

应用方收到通知后可主动拉取增量数据，减少轮询压力。

## 十一、安全与合规

### 11.1 数据脱敏

- 患者姓名、身份证号、手机号、地址等敏感信息建议脱敏后返回，或返回空值。
- 病历号、就诊号等业务标识可返回，用于关联查询。
- 如数据方无法脱敏，需由应用方在接收后处理，并在对接时明确。

### 11.2 传输安全

- 生产环境必须使用 HTTPS。
- 敏感接口建议启用双向 TLS（mTLS）。
- 接口密钥/Token 定期轮换，建议有效期不超过 90 天。

### 11.3 访问控制

- 接口应限制应用方服务器 IP 白名单。
- 按接口粒度分配最小权限，避免一次性暴露全部数据。
- 建议记录接口访问日志，包括调用方、时间、IP、请求参数摘要、返回记录数。

### 11.4 审计与合规

- 数据使用应符合《个人信息保护法》《数据安全法》《网络安全法》及医院内部数据管理办法。
- 建议数据方保留数据访问审计日志，支持按患者/时间/接口追溯。
- 研究导出场景需额外伦理/知情同意流程，不在本接口范围内。

## 十三、对接 Checklist

### 13.1 对接前需确认事项

- [ ] 确认认证方案（API Key / Bearer Token / mTLS / IP 白名单）
- [ ] 提供接口基础地址（Base URL）与测试环境地址
- [ ] 提供接口文档/Postman 集合/Swagger 地址
- [ ] 确认分页策略与最大 `page_size`
- [ ] 确认时间字段格式统一为 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM:SS`
- [ ] 确认 `patient_id`、`visit_id` 在所有表中的一致性
- [ ] 确认科室、药品、检查、检验、疾病等标准化名称
- [ ] 确认 `is_drug` 字段值域为 `是/否/未知`
- [ ] 确认统计聚合接口能否按科室、时间维度返回
- [ ] 确认实时状态接口（在院患者、床位）的更新频率
- [ ] 确认数据脱敏规则与返回字段
- [ ] 确认接口限流策略与 SLA

### 13.2 测试数据要求

- [ ] 提供测试环境账号与少量脱敏测试数据
- [ ] 测试数据应覆盖：单次就诊、多次就诊、有检查/检验/手术/医嘱、有再入院、有质控异常等场景
- [ ] 提供接口压力测试报告（尤其是医嘱、检验大表分页查询）
- [ ] 确认生产环境访问白名单（若需要）

### 13.3 上线前需确认事项

- [ ] 生产环境 HTTPS 证书有效
- [ ] 生产接口权限、IP 白名单配置完成
- [ ] 数据方监控告警与日志审计开启
- [ ] 应用方完成全量同步测试与增量同步测试
- [ ] 双方确认数据更新时延满足业务需求

## 十四、附录

### 14.1 字段命名约定

- 采用英文小写 + 下划线命名，如 `patient_id`、`admission_date`。
- 避免使用数据库保留字、中文拼音、无意义缩写。
- 同一语义字段在不同接口中名称保持一致。

### 14.2 常用时间字段说明

| 字段 | 含义 | 适用接口 |
|---|---|---|
| `admission_date` | 入院日期 | 入院、出院、就诊 |
| `discharge_date` | 出院日期 | 出院、就诊 |
| `exam_date` | 检查日期 | 检查 |
| `submit_time` | 检验送检时间 | 检验 |
| `surgery_start_time` | 手术开始时间 | 手术 |
| `order_start_time` | 医嘱开始时间 | 医嘱 |
